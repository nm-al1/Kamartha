# Follow-up audit: stage B functional, UI and accessibility

Date: 2026-10-31. Scope: stage B after the first four audit fixes. Method:
code inspection, real PostgreSQL with independent connections, computed contrast
ratios, and one throwaway widget test for the reload state. **No UI was edited
during this audit.** Findings below are evidence, not an approval to redesign.

## Confirmed findings

1. **HIGH, concurrent writes lose their CSRF token.** `BusinessRepository.write`
   fetches `/auth/csrf` before *every* write, and that endpoint rotates the
   session token. If two writes fetch a token before either posts, only the last
   fetched token is valid. Reproduction with two real connections and a barrier:
   `POST /rooms` returned **201** for one request and **403 `CSRF_REJECTED`** for
   the other. This is not data corruption, but two tabs or two concurrent payment
   submissions (the stage D concurrency case) can lose a request.
   Sources: `frontend/lib/core/business_repository.dart:28`;
   `backend/app/modules/auth/router.py:38-41`.
   Suggested direction: make the CSRF token stable for the session (for example a
   server-derived token) or stop rotating it on a read and cache it client-side.
   A client cache alone does not fix two tabs that refresh at different times.

2. **MEDIUM, login error survives a successful reload.**
   `AuthPage._bootstrap` clears `_busy` on success but never clears `_error`.
   After a failed bootstrap, tapping "Muat ulang" with the API available leaves
   the old error above a working form. A throwaway widget test failed on exactly
   this expectation (`Found 1 widget with text "Permintaan belum berhasil..."`).
   Source: `frontend/lib/features/auth/views/auth_page.dart:48-52`.

3. **MEDIUM, opening-record errors are not attached to fields.**
   The long opening form has no per-field validation or error text. Server
   failures are thrown as `Exception(apiError(...))` and shown once at the very
   bottom, after every occupancy and invoice row; the literal string therefore
   starts with `Exception:`. There is no scroll/focus to the first invalid input.
   `docs/design.md:223` requires the message near the field and focus on the first
   error. Sources: `frontend/lib/features/initialization/views/opening_record_form.dart:103-120,332-340`;
   `initialization_page.dart:148-149`.

4. **MEDIUM, authentication header contrast is below WCAG AA.**
   White text on the brand header `#F45A24` measures **3.32:1**. The AppBar title
   is 22 px regular (not large text), so AA requires 4.5:1. `docs/design.md:32-33`
   reserves `#F45A24` for identity/accent and specifies `#B9380B` for white-text
   actions, which measures **5.78:1**. Source: `frontend/lib/features/auth/views/auth_page.dart:169-173`.

5. **MEDIUM, typography tokens are still not applied.**
   `ThemeData` does not set a text theme, so regular body text inherits Material's
   14 px and `titleLarge` is 22 px. `docs/design.md:44` specifies 16 px for body
   and input, 14 px metadata, 24 px titles. This is the same open finding as
   `audit-001`, now re-confirmed after the fixes.

6. **LOW, shape tokens differ from the design.**
   `OutlineInputBorder()` defaults to a 4 px radius; `docs/design.md:46` specifies
   12 px for inputs. Material 3 `Card` defaults to 12 px; the design specifies
   16 px for information groups. Source: `frontend/lib/app/app.dart:87-91`.

7. **LOW, rupiah values have no thousands separators.**
   Recap, invoice and room rows render `Rp500000` rather than the documented
   examples such as `Rp1.500.000` (`docs/03-uml/uml.md:517`,
   `docs/testing/stage-b.md` examples). Values are correct; only scanning is
   harder. Sources: `initialization_page.dart:301,314,324`;
   `master_page.dart:129`. No currency formatter is used.

8. **LOW, current navigation location is not indicated.**
   Sidebar `ListTile`s and bottom-navigation `TextButton`s never show a selected
   state. This does not block navigation, but it weakens location feedback.
   Source: `frontend/lib/core/business_page.dart:40-43,65-67`.

## Resolution (2026-11-01)

The user approved all eight findings. They were implemented and verified:

1. **CSRF:** authenticated sessions now use one stable token derived with
   `HMAC-SHA256(ip_hash_secret, "kamartha-csrf:" + raw session token)`; only the
   token hash is stored. `GET /auth/csrf` no longer rotates it, and login returns
   the derived token. Preauth login/setup CSRF still rotates separately.
   Regression: two concurrent resident writes with one token both return **201**;
   repeated reads return the same token. The earlier reproduction was one 201
   and one 403.
2. **Stale auth error:** successful `_bootstrap` clears `_error`; a widget test
   fails on the old state and passes now.
3. **Opening form:** local date/integer-rupiah validation, inline `errorText`,
   focus on the first invalid field, mapping of server `error.fields`, and no
   `Exception(...)` wrapper. Widget tests cover invalid money and a server field
   error, including the absence of the `Exception:` prefix.
4. **Auth header:** `#B9380B` with white text, measured **5.78:1**.
5. **Typography:** 16 px body/input, 14 px metadata, 24 px titles.
6. **Shapes:** input radius 12, card 16, filled button 24.
7. **Rupiah:** `formatRupiah` groups thousands; applied to room, contract, recap,
   finalization and remaining-amount displays. Unit test covers positive, zero,
   negative and null values.
8. **Navigation:** rail and bottom navigation mark the current section; checked
   at 1280 and 360 widths.

## Concurrency checks that now pass

`backend/tests/integration/test_stage_b_concurrency.py` migrated a committed
throwaway schema in the isolated `kamartha_test` database, used independent
connections, and dropped the schema afterwards.

- Two finalizations with different keys: one 200, one 409 `MODE_REJECTED`; one
  finalization/lease/occupancy/invoice/responsible-history; zero payments.
- Two finalizations with the same key: both 200 with identical data; one
  materialized result.
- Two draft creations with the same key: both 201 with the same record; one
  record and one idempotency row.
- Two writes with the same session CSRF token: both 201, and repeated
  `/auth/csrf` reads return the same token.
- Three consecutive runs after the CSRF fix: **4 passed** each. Full backend
  suite: **87 passed, 38 subtests**, no skips, **90%** coverage.
- Room allocation is not part of stage B, so its race remains unproven until
  stage C provides the endpoint.

## Decision

The user approved findings 1–8. They are implemented and verified by the checks
above. Concurrency for finalization/replay/draft creation/CSRF is evidenced; it
is not a claim of complete stage B acceptance or of formal `test-plan.md`
results. Manual keyboard, screen-reader/axe, text-zoom and visual-baseline checks
remain open, so stage B still needs explicit user approval before stage C.
